# Прогноз платного хранения

Вкладка «Хранение» показывает график платы **за один день** на 30 дней,
начисление из последнего доступного отчёта, прогноз на завтра / +7 / +30 дней
и сумму за следующие 7 / 30 дней. Под графиком — товары с текущими складами,
ценами единицы и датами повышения, затем бесплатные лимиты каждой поставки.
Дата отсчёта — «По дату» в фильтрах. В прошлых датах используются только
отчёты, полученные для дня не позднее выбранного: новый повторяющий отчёт
не удаляет доступную старую версию. Склады/кластеры фильтруются после расчёта
общего бесплатного лимита SKU.

## Источники цены

[Официальный Seller OpenAPI](https://docs.ozon.com/api/seller/swagger.json)
проверен 09.10.2026: 482 операции. Для размещения используются уже собираемые
`/v1/report/placement/by-products/create` и
`/v1/report/placement/by-supplies/create`. В опубликованном контракте не найден
отдельный метод получения будущих тарифов хранения по складу и SKU.
`/v1/product/placement-zone/info` даёт зоны размещения, не цену хранения.
Новые запросы к Ozon для этой функции не добавляются.

Отчёт по товарам даёт дату, SKU, склад, количество, платное количество,
общий и платный объём в миллилитрах, категорию, тип, признак и начисленную
стоимость размещения. Поэтому цена определяется для каждой строки:

1. Если товар уже платный: начисление / платное количество на этом складе.
2. Если есть прежнее платное начисление этого SKU на этом складе: его цена,
   при наличии объёмов — пересчёт на текущий объём единицы.
3. Если SKU бесплатный: объём единицы × наблюдаемая цена литра для той же
   категории, типа и признака на том же складе. Явная пометка «Оценка цены».
4. Если собственного склада нет: тот же тип товара по другим складам,
   отдельно обозначенная оценка и предупреждение наверху.
5. Если цены нет или наблюдения несовместимы: неизвестная часть суммы,
   а не нулевая цена и не среднее между разными тарифами.

Наблюдаемая цена литра = начисление × 1000 / платный объём в мл. Округлённая
цена с точностью до копейки используется, только если воспроизводит каждое
наблюдаемое начисление с ROUND_HALF_UP. Иначе проверяется пересечение
интервалов, допускаемых округлением начислений; несовместимые цены не
усредняются. Данные для цены — максимум 30 предшествующих дней.

Это оценка по фактическим начислениям, **не будущий официальный тариф**.
Изменение тарифов, льгот, категории или особых условий склада неизвестно
до нового отчёта. Цена другого склада явно не считается подтверждённой.

## Бесплатные лимиты и расчёт

Колонки с датами в отчёте по поставкам описывают бесплатный лимит поставки,
не фактический оставшийся товар конкретной партии. Сводные строки SKU
отделены от поставок: текущий остаток из «Остаток на складах на (...)» хранится
в `stock_quantity`, поставочный лимит — в `quantity`, дата — `quantity_day`.
Они не складываются друг с другом. Склад поставки не обязательно совпадает
с текущим складом размещения; в интерфейсе это подписано.

На реальных отчётах 09.10.2026 сумма поставочных лимитов — 5 276, физическое
количество в отчёте начислений — 4 111, платных единиц — 308. Начислено
2 764,71 ₽; отчёт также включает вчерашние строки, которые не прибавляются
к сегодняшнему начислению. Эти числа — проверка источников, не константы кода.

Модель рассматривает лимиты одного SKU общими для его складов. Это согласуется
с большей частью текущего отчёта: `max(0, физический остаток − активный лимит)`
совпадает с платным количеством у 33 из 36 SKU. В трёх SKU есть расхождения;
их причина не доказана, дата перехода остаточного бесплатного количества
остаётся неизвестной. Наблюдаемое платное количество и начисление всегда
являются исходной точкой, не заменяются теоретическим пересчётом лимитов.

В неизменном остатке свободных единиц `F = Q − P`. Пока совокупный лимит больше
`F`, окончание его лишней части не увеличивает расходы. Из запаса лимита
сначала вычитаются самые ранние окончания. Когда действующий лимит становится
меньше `F`, соответствующие физические единицы переходят на платное хранение.
Физическое количество не увеличивается и не оплачивается дважды.

По текущим складам новые платные единицы распределяются пропорционально
бесплатному остатку SKU на каждом складе: это оценка распределения, а не
подтверждённая Ozon привязка конкретной бесплатной партии. Для отфильтрованного
склада используются все лимиты SKU, включая поставки на другие склады.

Дата «Окончание периода» считается последним бесплатным днём включительно;
платное хранение начинается на следующий день. Это явно показанное допущение:
счётчик дней из Ozon может отличаться на день, поэтому он показывается отдельно,
а не заменяет календарную дату. Одна поставка может иметь несколько отдельных
периодов бесплатного размещения: ключ включает её номер, склад, дату окончания
и категорию/тип/признак. Разные периоды не удаляются как дубликаты. Дубли одного
периода не умножают лимит; при конфликтующем количестве весь срок бесплатного
остатка SKU считается неизвестным.

Для неизвестных сроков показан диапазон: снизу — переход только по известным
датам, сверху — также вся часть с неизвестной датой. При неизвестной цене
верхняя сумма не выводится числом: «от ... + неоценённая часть».

## Допущения и эксплуатация

Основной сценарий: постоянный физический остаток, без продаж и новых поставок,
без изменения цен. Он отвечает на вопрос «сколько будет стоить этот остаток,
если он останется». Это не счёт Ozon и не прогноз движения товара: продажи
обычно снижают расходы, поставки/возвраты/перемещения могут их изменить.
При старом отчёте дата фактического начисления остаётся видимой и выводится
предупреждение. Отсутствующие сведения не превращаются в ноль.

Миграция `005_storage_cost_forecast.sql` добавляет объёмы/тип/дату/физический
остаток к существующим строкам, заполняет их из сохранённого raw JSONB и создаёт
`ozon.v_storage_unit_cost`. Исходники и все старые значения сохраняются.
View выбирает один отчёт на дату/SKU/склад/признак, не складывая повторения.
Будущие ежедневные отчёты сохраняют новые поля тем же сборщиком и расписанием.

`GET /api/storage/forecast?as_of=YYYY-MM-DD&sku=...&cluster=...&warehouse=...`
защищён входом и читает PostgreSQL через роль только для чтения. Вкладка
загружается отдельно при открытии; движения ползунка не делают HTTP-запросов.
Обращений к Seller или Performance API из этого маршрута нет. Внешние BI
могут читать `v_storage_unit_cost`, но будущие суммы/диапазоны считаются
в `storage_forecast.py`, не являются отдельной оплаченной финансовой таблицей.

Проверки: лишний лимит, дата включительно, пересекающиеся версии отчётов,
исторические цены, разные объёмы SKU, фильтры после глобального расчёта,
неизвестные цены/сроки, несовместимые тарифы, нулевое фактическое начисление,
дубли и миграция старых JSONB. Браузерный smoke проверяет отложенную загрузку,
график, 4 карточки, ползунок, раскрытие товаров и экран телефона без переполнения.
