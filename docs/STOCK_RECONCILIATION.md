# Как сверять остатки FBO

Официальный контракт методов и полей:
[Seller API OpenAPI](https://docs.ozon.com/api/seller/swagger.json).
Ежедневный сбор выполняет только методы чтения. Открытие страницы, переключение
фильтров и скачивание доказательств используют PostgreSQL и не обращаются к Ozon.

## Разные показатели

| Метод / поле | Что сохраняем и показываем |
|---|---|
| `/v1/analytics/stocks`: `available_stock_count` | Доступно к продаже, SKU × склад × день; используется для прогноза |
| `return_to_seller_stock_count` | К вывозу по заявке; хранится отдельно от доступного |
| `outbound_returns_picking`, `outbound_returns_ready_to_ship`, `outbound_returns_return_to_seller` | Этапы вывоза; не складываются с общим показателем вывоза |
| Остальные статусы `analytics/stocks` | Самостоятельные поля, доступны в раскрываемой сверке; сумма всех статусов не вычисляется |
| `/v3/product/info/list`: `stocks.stocks[].present` при `source=fbo` | «Сейчас на складе FBO»: независимый ответ, SKU × схема продаж × день |
| Там же: `reserved` | Зарезервировано, отдельная метрика |

Снимки двух методов сделаны в разное время. `present` нельзя автоматически
распределить по кластерам или превратить в сумму остальных статусов: для него
API не возвращает такой детализации. При выборе кластера/склада карточка этого
показателя показывает отсутствие разбивки. Дата и время независимого снимка видны.
Неизвестное поле не заменяется нулём, включая агрегаты с неполным покрытием.
Старые дни без ответа `product/info/list` не заполняются сегодняшними значениями.

## ПВЗ и архивные товары

ПВЗ действительно присутствуют в `analytics/stocks`: имя вида `ПВЗ_…`, иногда
отрицательный `warehouse_id`, тег `FBS_RETURN`. Тег сохранён буквально и сам по
себе не означает, что продавец работает по FBS. Строки остаются в исходном ответе
и фактах. Класс локации и название фиксируются в каждой строке дневного снимка;
изменение текущего справочника не переименовывает историческую классификацию.
Миграция классифицирует прежние строки по их сохранённым ответам API.

По умолчанию ПВЗ скрыты из карточек, графика, складов и подсказок по рекламному
остатку. Они учитываются отдельно в сверке. «Показать ПВЗ» возвращает их в срез.
В фильтре складов также отсутствуют чужие/неиспользуемые узлы: показываются только
локации снимка или отправлений данного кабинета за выбранный период.

`/v3/product/list` не возвращает названия и исключает архив из `visibility=ALL`.
Архив запрашивается отдельно ради полной истории и внешних ключей старых заказов.
Теперь отдельный `product/info/list` заполняет названия и статус архива независимо
от наличия строк остатков. Дневной исходный ответ хранится в `product_info_snapshot`,
а независимые количественные поля — в `inventory_daily`.

Архив без доступного остатка или товаров к вывозу скрыт в фильтре по умолчанию;
«Показать архивные товары» возвращает его. Архивный товар с положительным остатком
остаётся доступным, чтобы не скрыть товар, требующий действий. Исторические
заказы и факты не удаляются при скрытии товара.

## Сохранённые ответы

На вкладке «Остатки» доступны «Ответ API: остатки» и «Ответ API: товары».
Это полные исходные тела ответов за указанные на экране даты, включая скрытые
ПВЗ и архив; точные времена и запросы SKU/product_id находятся рядом с ответом.
Заголовки авторизации не включаются. Скачивание требует обычного входа в сервис.

`GET /api/stocks/source?day=YYYY-MM-DD&kind=analytics|catalog` возвращает JSON.
Дополнительные `sku` и `warehouse` сужают строки остатков; такой файл помечен
`filtered`. Для каталога поддерживается SKU. Несуществующая дата возвращает 404,
а не соседний снимок. Для сверки кластера используйте полный ответ и его
`cluster_id`: кнопки на странице всегда скачивают полные ответы за день.

## Ограничения запросов

Имена загружаются одним дополнительным запросом на <=1000 product_id в сутки.
Сохраняются только безопасные заголовки лимитов (`Retry-After`, `RateLimit-*`).
После первого 429 применяется `Retry-After` и минимум 60 секунд; после второго
429 того же метода за 15 минут общий клиент откладывается минимум на 15 минут.
Длительный cooldown переживает рестарт и продолжает работу следующим запуском
systemd, без ожидания и повторных вызовов внутри текущей задачи.

Число «около 6000» можно подтвердить только сопоставлением конкретного показателя
кабинета, даты, выбранных товаров и статусов. Сервис показывает ответы методов
и не подгоняет сумму под ожидаемое число.

## Проверка и выпуск

Интеграционные тесты на отдельном PostgreSQL проверяют названия товаров без
остатков, архив с положительным остатком, сохранение ПВЗ, разные показатели,
NULL, отсутствие выдуманной географической разбивки, защиту исходных ответов,
атомарность неполных ответов и миграцию прежних опубликованных снимков.
Мобильная проверка покрывает переключение ПВЗ и скачивание JSON без вызовов Ozon.

Исправление находится в отдельной ветке `fix/stock-reconciliation` поверх
`feat/ozon-performance-analytics`. Основная ветка и PR рекламы не изменяются.
Перед миграцией создаётся копия БД. Для первого исправления названий можно
импортировать уже сохранённый полный ответ через `save_product_info`, не делая
новый запрос и не перезаписывая опубликованный дневной снимок остатков.
