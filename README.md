# Ozon · Пульс

Ежедневная аналитика FBO: остатки по SKU, складу и кластеру, заказанные товары
и сумма заказов, направления отправки, прогноз исчерпания остатков и сроки
бесплатного хранения по отдельным поставкам. Интерфейс рассчитан на телефон.

Развёрнутый сервис: **https://185.255.132.160/**. Логин `analytics`;
пароль — `ADMIN_PASSWORD` в защищённом локальном `.env`. На сервере конфигурация
находится в `/etc/ozon-analytics/service.env` (root, 0600).
Секреты, SSH-ключи, исходные выгрузки и снимки экрана в Git не попадают.

## Что сохраняется

| Таблица / представление | Назначение и детализация |
|---|---|
| `seller_account`, `product` | Кабинет и справочник SKU. Артикул не обязан быть уникальным |
| `warehouse`, `cluster`, `macrolocal_cluster` | Три отдельные сущности; идентификаторы кластеров разных API не смешиваются |
| `ingest_run`, `api_response` | Попытки получения полного снимка и исходные ответы остатков |
| `stock_daily` | Дата × SKU × физический склад, остатки, кластер **на дату снимка**, показатели Ozon |
| `published_snapshot` | Один выбранный успешный снимок кабинета на день |
| `v_stock_daily`, `v_cluster_stock_daily`, `v_macrolocal_stock_daily` | Опубликованные остатки на складах и агрегаты |
| `posting`, `posting_item`, `v_sales_fbo` | Заказы FBO и позиции; дата заказа, количество, цена, валюта, статус, склад, откуда/куда |
| `sales_coverage` | Полностью выгруженные дни заказов; отличает отсутствие загрузки от отсутствия продаж |
| `sales_daily`, `analytics_coverage` | Официальные `ordered_units`/`revenue` по SKU и UTC-дню, отдельно от FBO по московским дням |
| `storage_report`, `storage_row` | Отчёты хранения, исходные колонки и строки: SKU, склад, поставка, остаток партии, дни, дата конца периода, начисления |
| `api_call`, `api_cooldown`, `job_run` | Аудит, устойчивые к перезапуску лимиты, результаты фоновых задач |
| `host_metric`, `backup_run` | CPU/RAM/диск/swap и состояние резервных копий |

Полная структура, типы, индексы и ограничения — в `db/001_schema.sql` и
`db/002_service.sql`; примеры аналитических запросов — в `db/queries.sql`.
Все миграции применяются последовательно и учитываются в `schema_migration`.

История остатков начинается с первой успешной выгрузки: API текущих остатков
не восстанавливает прошлый год. Первая загрузка заказов охватывает 14 последних
дней; ежедневные факты далее накапливаются без удаления за год.
Дни без снимка и отсутствующие значения не заменяются нулями. Неуспешная
попытка не заменяет опубликованный снимок. Средние продажи Ozon, повторяющиеся
в нескольких строках склада одного кластера, не суммируются.

Основные показатели продаж — **заказанные** товары и сумма `quantity × price`
до комиссий. Отмены видны отдельно и включены в валовые заказы; для прогноза
они исключаются. Направления `cluster_from`/`cluster_to` сохраняются как
исходные коды/названия регионов, а не выдуманные числовые cluster_id.
Если на дату старого заказа нет снимка для подтверждения числового кластера,
он остаётся неизвестным: такие заказы доступны по складу и направлению,
но не попадают в фильтр неподтверждённого числового кластера.

## API и расписание

Официальный контракт: [Seller OpenAPI](https://docs.ozon.com/api/seller/swagger.json),
проверен 07.10.2026. Используется только разрешённый список методов чтения:

| Метод | Использование |
|---|---|
| `/v3/product/list` | Активные и отдельно архивные SKU, курсорная пагинация |
| `/v2/cluster/list` | Макролокальные кластеры |
| `/v1/analytics/stocks` | Все строки SKU × склад без сужающих фильтров, пачки до 100 SKU |
| `/v3/posting/fbo/list` | Заказы FBO, до 100 отправлений на странице, курсор и фиксированный диапазон времени |
| `/v1/analytics/data` | `ordered_units` и `revenue`, измерения `sku`, `day` |
| `/v1/report/placement/by-products/create` | Создание отчёта о начисленном хранении |
| `/v1/report/placement/by-supplies/create` | Создание отчёта по поставкам и бесплатным срокам |
| `/v1/report/info` | Проверка готовности; XLSX скачивается с подтверждённого домена Ozon |

Лимиты официального контракта: общий — 50 запросов/сек на Client-Id,
`analytics/data` — 1/мин и 50/день без Premium, каждый метод создания отчёта
хранения — 5/день. Наш сборщик использует **не чаще одного вызова в 5 секунд**,
аналитику — не чаще одного в 65 секунд; максимум 200 обращений/UTC-день,
45 к аналитике и 2 создания каждого вида отчёта. Фактический ежедневный
объём при текущем кабинете значительно меньше. Другие интеграции с тем же
Client-Id имеют собственные запросы и должны учитываться при росте нагрузки.

При 429 соблюдается `Retry-After`, пауза минимум 60 секунд; сетевые ошибки и
5xx — максимум три попытки с задержками. 400/401/403 не повторяются сразу:
ошибочный метод откладывается на сутки, при ошибке авторизации — весь клиент.
Неопределённый результат создания отчёта никогда автоматически не создаёт
новую копию. Сохраняется код отчёта, незавершённый отчёт опрашивается позднее.

Первая ежедневная загрузка — **09:10 по Москве**. Таймер возобновления работает
каждые 30 минут в дневные/вечерние часы; до 09:10 сборщик ничего не запрашивает.
Успешные остатки, продажи и отчёты повторно в этот день не загружаются.
После накопления начальной истории продажи обновляются за последние три дня
и отдельно — старые незавершённые отправления. В первый день используется
14-дневное окно. Сегодняшние цифры — на время загрузки, это ежедневная
аналитика, не поток в реальном времени. Нажатие «Обновить» перечитывает БД.

Performance Client ID/secret сохранены в ENV для последующего модуля рекламы;
данная версия не обращается к Performance API и не меняет кампании.
Документация: [Performance API](https://docs.ozon.ru/api/performance/).

## Прогноз и хранение

Прозрачная базовая модель: доступный остаток / средние заказы за 14 полных дней.
Спрос склада для расчёта по кластеру группируется по составу складов выбранного
снимка. Пока истории недостаточно, для кластера используется `ads_cluster`
Ozon (средние продажи за 28 дней), если показатель есть. Для отдельного склада
без своей истории прогноз неизвестен. Нет спроса — нет выдуманной даты
исчерпания. Дефицит способен занижать наблюдаемый спрос; сезонность, акции
и будущие неподтверждённые поставки модель не предсказывает.

Срок поставки задан `REPLENISHMENT_LEAD_DAYS=14`, запас безопасности —
`SAFETY_STOCK_DAYS=7`; это стартовые допущения, изменяемые в ENV. Показываются
дни до исчерпания, ориентировочная дата, дата заказа пополнения и количество.
Товар в пути виден отдельно и автоматически в доступный остаток не включается.

Дни бесплатного хранения взяты из реального отчёта Ozon **по каждой поставке**.
Сводные строки SKU не считаются сроками партий. Счётчик Ozon сохраняется
самостоятельно: он может отличаться от простого вычитания календарных дат.
Предупреждение возникает для партии с положительным остатком и ≤7 дней.
Начисления берутся из отчёта по товарам; перекрывающиеся дневные отчёты
не складываются дважды. Склад сопоставляется только по однозначному точному
нормализованному названию, числовой кластер — по снимку того же дня.

## Интерфейс и готовые BI-продукты

Развёрнут собственный мобильный интерфейс FastAPI + обычный HTML/JS:
пять разделов, карточки, даты/товар/кластер/склад, графики, предупреждения,
защищённый вход и ярлык на домашнем экране. Данные не кэшируются для работы
офлайн. Предупреждения отображаются в интерфейсе; внешняя доставка уведомлений
в Telegram/email в этой версии не подключена.

Из готовых продуктов для самостоятельного построения произвольных отчётов
подходит [Metabase](https://www.metabase.com/docs/latest/databases/connections/postgresql):
он подключается к PostgreSQL и предоставляет конструктор и SQL-редактор.
[Superset](https://superset.apache.org/docs/intro/) — другой вариант BI.
Они не установлены: текущие необходимые срезы реализованы в мобильном сервисе.
Для будущего BI подготовлен отдельный read-only пользователь `ozon_web`;
новому BI лучше выделить собственную роль с SELECT только на аналитические
представления, без исходного аудита. PostgreSQL доступен только локально;
для клиента с компьютера используйте SSH-туннель, не открывайте 5432 наружу.

## Сервер и размер данных

PostgreSQL 16 установлен нативно, данные `/var/lib/postgresql/16/main`,
30 соединений, 128 МБ shared_buffers. Приложение и задачи — отдельный
пользователь `ozon` и systemd, ограничения памяти 384/512/128/256 МБ
для веба/сборщика/мониторинга/копирования. Это ограничения, не постоянный расход.
Существующие Docker-приложения и их базы сохранены.

| Вариант PostgreSQL | Практические особенности |
|---|---|
| Нативный — выбран | Простой systemd/pg_dump, отдельная от Docker работа; обновления и пути обслуживаются средствами Ubuntu |
| Docker с постоянным volume | Удобна фиксация версии и перенос; данные живут в volume и не удаляются от падения Docker. Удаление volume/диска опасно, резервные копии всё равно нужны |

Измерено 07.10.2026: 421 строка остатков, 37 SKU с возвращёнными остатками,
65 складов, 23 кластера; 598 отправлений за окно 14 дней плюс текущий день.
В справочнике также есть архивные/исторические товары. База после первого
запуска — около 12 МБ, включая системный минимум PostgreSQL. Не все
комбинации SKU × склад присутствуют в API, отсутствующие строки не достраиваются.

421 × 365 = примерно 154 тыс. строк остатков/год. При текущем объёме
ориентир всей БД с заказами и отчётами — **0,5–2 ГБ за год**, без WAL и копий;
это плановая оценка, уточнять по фактическому росту. Полная плотная сетка
100 SKU × 65 складов × 365 даёт 2,37 млн строк, ориентир только остатков
с индексами/исходными ответами — 1–3 ГБ. Количество физических единиц в остатке
само по себе строк не добавляет; число отправлений и партий — добавляет.
Выделить 10–20 ГБ под БД, рабочее пространство и восемь копий достаточно
как стартовый запас, затем измерять `db/queries.sql`, запрос №5.
Диагностические тела успешных API-вызовов старше 30 дней очищаются;
факты заказов, снимки и исходные ответы остатков/строки отчётов не удаляются.

Мониторинг каждые пять минут, история 90 дней. Предупреждение в мобильном
разделе при RAM/диске ≥85%; видны CPU, свободные гигабайты, ответы 429 и копии.

## HTTPS и эксплуатация

В существующий nginx добавлен отдельный IP-host; сайт gemtools.ru продолжает
работать по своему имени. Предыдущая конфигурация сохранена рядом как
`default.conf.before-ozon-20261007`. Веб слушает Docker gateway
`172.17.0.1:8090`, PostgreSQL — `127.0.0.1:5432`; публичный доступ через nginx.

Используется доверенный сертификат Let's Encrypt для IP, короткого срока;
[официальные инструкции](https://letsencrypt.org/2026/03/11/shorter-certs-certbot.html).
Certbot ≥5.4 установлен отдельно от прежнего контейнера, конфигурация
`/etc/ozon-analytics/letsencrypt`; продление дважды в день. Deploy-hook копирует
PEM в volume существующего nginx и проверяет/reload-ит прокси.

```sh
ssh ozon-analytics
systemctl status ozon-web
systemctl list-timers 'ozon-*'
journalctl -u ozon-collect.service -n 30 --no-pager
systemctl start ozon-collect.service
systemctl start ozon-monitor.service
systemctl start ozon-backup.service
curl --fail https://185.255.132.160/healthz
```

SSH-ключ выделен для проекта, парольный доступ добавлением ключа не отключался.
Локальная `.env` содержит и исходные доступы, и новые пароли приложения/БД;
серверный ENV содержит только нужную сервисам конфигурацию, без SSH-пароля.

## Резервные копии и восстановление

Воскресенье 03:30 по Москве, восемь последних недель в
`/var/backups/ozon-analytics`, права 0700/0600. Архив содержит custom pg_dump,
manifest SHA-256 и исходные XLSX. Проверка pg_restore --list, потоковые хеши,
атомарная запись и ротация только после успешной новой копии. Пароли ролей,
ENV и TLS-ключи в этом архиве не содержатся — защищённый ENV нужно сохранить
отдельно. Код хранится в Git.

Первая копия создана вручную и восстановлена в отдельную временную БД;
проверено чтение 421 строки остатков, 598 отправлений и 963 строк отчётов.
Тестовая база после проверки удалена, рабочая БД не изменялась.

```sh
cd /opt/ozon-analytics
# root; имя архива подставить фактическое:
PYTHONPATH=src .venv/bin/python ops/verify_restore.py /var/backups/ozon-analytics/ozon-YYYYMMDDTHHMMSSZ.tar.gz
```

**Внешнее хранилище пока не подключено:** пользователь ещё не предоставил
адрес и доступ. Для S3/другого поддерживаемого хранилища настроить защищённый
rclone config, добавить в service.env `BACKUP_REMOTE=remote:bucket/ozon`
и `RCLONE_CONFIG=/etc/ozon-analytics/rclone.conf`, установить rclone.
До этого `offsite=false` честно отображается в интерфейсе. Локальная копия
не защищает от потери самого сервера. Внешние копии с шифрованием лучше
настроить через rclone crypt после получения места хранения и ключа.

## Разработка и проверка

Python ≥3.12, зависимости фиксируются `uv.lock` и hash-pinned `requirements.txt`.
Безопасный тестовый контур не обращается к Ozon: HTTP transport подменён.
`TEST_DATABASE_URL` должен явно указывать disposable-базу с `ozon_test` в имени:
фикстура удаляет только её схему перед каждым тестом.

```sh
uv sync
docker run -d --rm --name ozon-service-tests -e POSTGRES_HOST_AUTH_METHOD=trust -p 127.0.0.1:55432:5432 postgres:16-alpine
docker exec ozon-service-tests createdb -U postgres ozon_test
TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55432/ozon_test uv run pytest -q
docker exec -i ozon-service-tests psql -U postgres -d ozon_test -v ON_ERROR_STOP=1 < db/tests.sql
uv run ruff check src tests ops/*.py
uv run playwright install chromium
uv run python tests/browser_smoke.py --base-url https://185.255.132.160
docker stop ozon-service-tests
```

После изменения зависимостей:
`uv export --no-dev --no-emit-project --output-file requirements.txt`.
На сервере `.venv/bin/pip install -r requirements.txt`, миграции запускаются
с EnvironmentFile от systemd или защищённой передачей ENV. Не печатайте ENV
и не переносите локальный SSH-пароль на сервер.
Шаблоны systemd и nginx находятся в `ops/`; `provision_database.py` запускается
root после установки зависимостей и заполнения защищённого service.env.
Web-роли требуются USAGE на схему и SELECT на таблицы/представления;
она не владеет схемой и имеет `default_transaction_read_only=on`.

Ветка разработки — `feat/ozon-mobile-analytics`, main содержит только
разрешённый пустой начальный коммит. CI/CD не настраивается; слияние PR делает
владелец. Деплой этой ветки на сервер — ручной, последующие обновления тоже.
